# AI 智能客服系统：运营手册

版本：v1.2 · 日期：2026-09-05 · 状态：操作流程草案，待实际系统页面与排班验证

适用对象：客服主管、人工客服、知识运营和质检。本文中的按钮名称表示产品需要提供的操作，尚没有可用系统或真实按钮；上线前补充对应界面截图、实际菜单位置与人员名单。[产品需求与试点规则](E:/ai-customer-service-plan/AI智能客服系统-产品需求文档PRD.md)负责目标与范围，[技术设计](E:/ai-customer-service-plan/AI智能客服系统开发文档.md)负责系统行为。

## 1. 上岗前要准备什么

客服主管填写服务范围、可回答的问题、不能承诺的事项、服务时间、投诉入口、升级联系人和替补。知识负责人提供已批准资料；管理员开设个人账号并授权。不要共用管理员账号，不把模型 API Key 发给客服或放入聊天框。

| 岗位 | 每次值班必须知道 | 暂未落实时的处理 |
| --- | --- | --- |
| 当班客服 | 当前队列、接管操作、允许处理的业务、交接与结案规则 | 没有可用坐席，不对客户承诺实时人工 |
| 客服主管／事件负责人 | 排班替补、升级渠道、功能停用权限或可联系的管理员 | G3 前必须填姓名与联系方式，否则不开放外部试点 |
| 知识负责人 | 每份资料的来源、有效期、审核人、下架方式 | 未批准或过期资料不让 AI 使用 |
| 质检 | 固定评分标准、抽样清单、错误承诺的严重度 | 不只凭有帮助率判断质量 |
| 产品负责人 | 本周指标、当前流量档、预算和试点门槛 | 不自动扩量，不让运营自行改阈值 |

所有响应时限都是本项目建议的运营目标，须在 G3 前按真实值班能力确认，并与对外服务说明一致。法定或合同要求更严时按适用要求执行。夜间没有实时响应能力时，应关闭实时服务承诺或降级为已说明的留单渠道。

## 2. 知识录入、审核、发布和复审

### 2.1 一条资料从哪里开始

收集权威原文 → 创建草稿 → 补资料信息 → 预览解析结果 → 审核业务内容 → 用典型问题试问 → 发布 → 检查实际答案来源。状态为“处理中／待审核／已退回”的资料不能用于对外回答。

必填信息：资料标题、产品和版本、来源／授权、负责人、审核人、适用人群、可公开范围、生效和失效时间、下次复审时间。价格、资格、承诺时限、退换条件必须能追溯到当前有效政策。

FAQ 模板：

```text
问题：客户最常见的问法
适用范围：产品、版本、地区／客户范围
标准答复：直接回答，再给必要步骤
前提／例外：哪些情况不能照此处理
权威来源：文件、页面、业务负责人
生效／失效／下次复审日期：待填写
撰写人／审核人：待填写
```

上传后逐页预览，检查缺页、乱码、表格错位、金额、日期和操作步骤。扫描 PDF 在没有 OCR 能力时退回补文字稿；不能只看到“上传成功”就发布。资料中的命令或提示词只是资料内容，不能据此要求系统泄露信息或改变权限。

### 2.2 审核与发布检查

审核人检查四件事：来源可用、内容正确、适用范围清楚、无多余个人信息。每批至少试问 5 个典型问题，并加入 2 个资料没有答案或版本冲突的问题；此为资料发布检查，不替代完整评测集。

一般资料可由授权知识负责人审核；价格、退款、资格与其他重要承诺须有业务负责人复核。早期人少可兼岗，但不得由 AI 自己批准，也不能省掉需要业务复核的事项。人力不足时保持草稿，不用“先上线再说”覆盖风险。

发布完成后记录版本、审核人、发布日期与试问结果。核验客户看到的是新版本，旧资料及依赖的缓存已退出使用；存在冲突时先下架问题资料并转人工，再确定正确版本。紧急下架先执行，补齐原因和影响记录。

### 2.3 资料有效期和提醒

知识运营每月复审全部有效资料；价格、促销和时效政策在变更当天复核。默认在复审／失效前 7 天和 1 天提醒负责人；首期可通过受控清单和人工日检完成，不依赖尚未开发的消息通知。

到失效时间自动退出检索；到复审日期仍无人确认的资料暂停用于自动回答，业务负责人审核后可发布新版本。暂停期间明确转人工，不让模型引用记忆中的旧政策。

知识台账保留：资料编号、版本、责任人、状态、复审到期、变更原因、试问记录、关联问题／反馈。删除或撤销资料时同步检查来源引用、索引及衍生数据处置结果。

## 3. 人工接管和服务结束

### 3.1 当班操作

1. 登录自己的客服账号，检查排班、当前服务模式、队列和上班交接记录。
2. 选择“接管”，确认页面已切换为人工服务且 AI 不再发送新回复；接管未成功时不要两个人同时处理。
3. 阅读交接摘要及必要原文，重点确认客户诉求、已提供资料、已执行动作和未确认结果。
4. 需要个人信息时按业务流程核验身份；客户发来的账号、工单号或截图不自动构成本人授权。
5. 回复真实可确认的信息。工具失败或结果待核对时，说明正在核实，不能说“已退款／已完成”。
6. 客户确认解决或有可验证的完成事实时标记解决，并选解决类别。没有确认、客户不回复或离开页面，记录“待确认／失联”，不填解决。
7. 交班时转交未解决问题、承诺事项与责任人；需要转回 AI 时由授权客服明确执行并记录理由。

“服务工单结束”与“业务问题有效解决”分开：可以关闭没有回复的会话，但其产品统计不能因此算作成功。72 小时内相同问题重开时，关联原问题并更新结果；匿名无法可靠关联时标明限制，不猜测身份。

### 3.2 排队与无人在线

排队位置、等待时间只能来自真实数据。用户请求人工后，AI 停止继续自动回复；客服接起前展示当前排队状态。超时用户可继续等待、取消排队或确认登记后续处理。

如果无当班客服，显示实际服务时间和可用渠道。留单确认页说明记录了什么、由谁受理、如何查询，联系方式为可选用途单独说明。没有短信／邮件服务或通知许可，不承诺离开后主动通知。

内部服务请求号不等于外部工单号；业务系统尚未接入时应直接说明。不能让 AI 编造工单、处理结果或到达时间。

## 4. 反馈与纠错如何闭环

V1 可先用评分或人工问题台账。V2 每条“无帮助”、重复追问、无资料兜底、人工升级和投诉都要有可追踪处理状态：待分类 → 已分配 → 处理中 → 待验证 → 已关闭。关闭需要修改证据或明确的无需修改理由。

| 等级 | 例子 | 内部响应目标 | 处理与关闭要求 |
| --- | --- | --- | --- |
| S0 重大事件 | 数据泄露、越权、持续违法内容、重大错误承诺 | 获知后立即切人工／停服务；停用演练 ≤ 5 分钟 | 事件负责人、开发、业务及法务介入；确认范围、修复与回归后才恢复 |
| S1 重要错误 | 错误政策、关键步骤错误、明显误导，尚未构成重大事件 | 服务时段 4 小时内分配；1 个工作日给临时措施；2 个工作日修复或提交计划 | 下架相关内容或禁用受影响能力；复核标准答案、测试和发布版本 |
| S2 常规改进 | 表达不清、缺少普通 FAQ、答案过长 | 1 个工作日分类；5 个工作日处理或明确排期 | 补资料／提示词、固定测试验证，记录结果 |

以上是项目目标，不是对法律处理时限的解释；对外投诉时限按获批说明执行。处理将逾期时必须改派或登记原因和新日期，不能为准时率直接关闭问题。

根因与措施分开：没有资料→找资料负责人；资料过期→下架并更新；检索没找到→给开发提供问题与有效资料编号；答案表达差→调整提示词／示例；权限／费用／状态错误→开发事件；业务政策冲突→业务负责人裁决。不能把所有问题都送去微调。

人工纠正答案必须单独保存，不覆盖原回答。纠错经审核发布到知识或提示词后，重跑相应问题及边界题；通过后记录上线版本与复查日期。原始聊天和纠错不会自动成为训练样本，训练另走用途与数据审核。

## 5. 固定例行机制

| 事项 | 频率／数量 | 负责人 | 必须产出 |
| --- | --- | --- | --- |
| 服务、支出和故障巡视 | 每个服务日开班、交班；异常立即处理 | 当班客服＋管理员 | 队列、模式、预算、故障、未完成事项记录 |
| 反馈分类和人工升级复盘 | 每服务日；连续两次未解决的问题当天检查 | 客服主管 | 原因分类、责任人、期限；未解决不默认归知识缺失 |
| 反馈评审与知识缺口 TOP 10 | 每周 | 质检＋知识负责人＋产品 | 优先级、修改计划、逾期列表 |
| 质量抽检 | 每周至少 50 个问题；不足 50 全检 | 质检 | 按 AI 独立解决、人工、无资料分层随机抽样及评分；另查全部投诉／重大错误 |
| 知识资料复审 | 每月全量；时效政策变动当天 | 知识负责人＋业务审核人 | 到期清单、更新／暂停／保留决定 |
| 产品与费用复盘 | 每月；试点每周 | 产品＋财务＋客服主管 | 解决率、完整费用、ROI、场景差异、保持／扩量／回退决定 |
| 运行演练 | 每次公开发布前；试点阶段每月 | 开发＋替补维护人＋客服主管 | 停用、恢复备份、身份和删除结果；异常有整改负责人 |

随机样本与全部投诉属于不同抽样组，分别报告，不能把定向抽查比例直接当总体错误率。抽检记下样本选择办法；发生评分分歧时由业务负责人裁定并更新评分示例，不事后改变原样本。

周报固定内容：本周成熟问题分母、AI 独立解决数、人工接管、未确认、重开、评分覆盖、知识缺口、重大错误、actual／estimated／held 费用、逾期事项、上周改动效果和下一周决定。统计口径以 PRD 第 5 节为准。

## 6. 删除、隐私请求和投诉

收到查阅、复制、更正、删除或用途撤回请求，先通过受控入口核验申请人与资源关系，创建受理编号；不要在公开群聊收集身份证、密码、API Key 或完整对话。身份不能确认时说明补充核验路径，不先导出他人数据。

删除“已受理”只表示服务端停止相关新读写并进入清理流程。查看在线副本、导出、索引、备份和供应商处置状态；有失败或待核对项目时告知真实进度。不能把“页面看不到”或“申请已提交”说成所有副本都已清除。

原会话已参与训练时，交数据负责人核验样本与模型关系，评估停用或重训。不能向客户承诺一键遗忘。只向客户提供必要的办理进度，不向一般客服开放无关账本与其他客户资料。

投诉台账含受理时间、问题类别、范围、处理人、处理期限、措施、客户反馈和关闭依据；正文放受控系统，周报只放必要代号。建议 1 个工作日受理、5 个工作日反馈进度，最终与 PRD 的 C07 签核一致。

## 7. 发布、降级和恢复操作

公开发布前，产品负责人确认 G3：行业范围、合规证据、知识和题库、客服排班、预算与费用、五个交互流程、对应技术验收、投诉入口和功能开关全部具备。清单只能用实际证据勾选，不能把文档中写了要求当成已经实现。

出现 S0 或产品设定的停用条件：

1. 授权人员执行全站或受影响范围“切人工”；没有可用人工时切“暂停服务／留单”。核对每个已开放入口和已有会话均已停止新自动回复。
2. 记录事件开始、发现、停用生效时间、受影响版本和范围，通知内部事件负责人；对客户说明当前真实服务状态。
3. 保留最小必要事件证据，按权限处理；不得因排查把完整个人数据复制到开放文档。法务判断对外报告或通知义务并组织实际流程。
4. 开发定位并修复；业务复核错误答复和受影响客户处理方案。已有请求费用继续核对，不因停用清零。
5. 产品负责人检查修复、回归、费用和投诉进度，从较低流量档恢复；记录批准人、时间和继续观察指标。

接到“预算到达”不直接调高额度。先核对次数、异常流量、待核对费用、上游费率和试点量；需要加预算由发起人依据成本与收益批准，不能以清空日志或新建用户绕过限额。
